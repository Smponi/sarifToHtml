How the prototype is split

The main flow is intentionally direct: SARIF in, findings normalized, HTML out. The CLI orchestrates file I/O and flags, while parsing, normalization, and rendering decisions live in separate packages.

PathResponsibility
cmd/sarif-htmlCLI flags, file I/O, CI exit-code behavior, and renderer option wiring.
internal/sarifFocused SARIF 2.1.0 model and JSON parsing.
internal/reportNormalization into findings, summaries, fingerprints, snippets, baselines, and merged reports.
internal/htmlVersioned template data, the embedded default template, and custom HTML rendering.
docsProject documentation as static HTML pages.
examplesSmall SARIF examples for development and demos.

Data Flow

  1. The CLI opens one or more SARIF files.
  2. internal/sarif.Parse validates SARIF 2.1.0 and decodes JSON.
  3. internal/report.FromSARIF extracts findings, rule metadata, locations, and snippets.
  4. internal/report.Merge sorts findings and rebuilds the summary.
  5. internal/html.NewTemplateData builds the versioned sarif-html.template.v1 contract.
  6. internal/html.Render renders either the embedded default template or an explicitly provided custom template.
Why this boundary exists

Renderers should not depend directly on raw SARIF JSON. The internal report model is where duplicate handling, severity behavior, fingerprints, snippet hydration, and baseline state matching stay controlled.

Template boundary

Custom templates use Go html/template and receive deterministic helpers for severity classes, line formatting, source links, and detail detection. SARIF data is escaped by default; the template file itself is trusted input.
